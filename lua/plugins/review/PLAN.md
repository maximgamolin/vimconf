# План: локальное MR-ревью в Neovim (рабочее название — `review`)

> **Статус (23.08.2026): этапы 0–5 реализованы, этап 6 — частично.**
> Модули: `store.lua`, `session.lua`, `comments.lua`, `panel.lua`, `visited.lua`,
> `main.lua`; тесты `tests/run.sh` (5/5); шаблон `fix-review.md`.
> Из этапа 6 сделано: дрейф-детект (⚠ в шапке замечания), `]r`/`[r`,
> пункт меню Review (quickui), раздел в шпаргалке `:Hlp`,
> `:ReviewPick` — пошаговый выбор веток/коммитов (telescope dropdown
> с фильтрацией набором текста, fallback `vim.ui.select`), кликабельные
> «ветка@hash ▾» в шапке diff (клик слева — сменить базу, справа — голову,
> вторая сторона сохраняется), кнопки «‹ пред / след ›» в шапке (навигация
> по изменениям, как ]c/[c), отключение neominimap во вкладке ревью.
> Осталось: счётчик в airline, обработка rename, проверка «не мержить с
> непустой .review», открытие изменённого файла как diff при goto-переходе.
> Ограничение v1: замечания пишутся только на правой стороне diff'а
> (привязка к строкам новой версии — решение из ТЗ).

Handoff-план для реализации по этапам. Каждый этап самодостаточен: можно отдать
отдельной сессии Claude Code. Контекст: пользователь ревьюит большие изменения,
написанные Claude Code, в стиле GitLab MR — но полностью локально, без форджа.

## Принятые решения (зафиксированы с пользователем)

| Вопрос | Решение |
|---|---|
| Имена файлов замечаний | Путь через `__`: `src/app/main.py` → `.review/src__app__main.py.md`, все файлы в одной папке |
| Потребитель замечаний | Claude Code: пишем замечания → коммитим → `/fix-review` исправляет и удаляет файлы |
| Якорь строки | Номер строки **новой** версии + цитата строки кода + hash коммита ревью (три независимых якоря) |
| Сравнение по умолчанию | Текущая ветка против merge-base с main (three-dot, как в GitLab MR); произвольные пары ревизий — выбором |

## Вердикт build-vs-buy (по итогам исследования, август 2026)

**Строим свой тонкий слой поверх готового diff-движка.**

- **Diff-движок: [codediff.nvim](https://github.com/esmuellert/codediff.nvim)** (★1527, активен).
  Даёт из коробки: side-by-side ⇄ inline (unified) переключение, панель-explorer
  изменённых файлов, сравнение произвольных ревизий, посимвольную подсветку
  (алгоритм VSCode). Diff-рендеринг — самая дорогая часть, её не пишем.
- **Слой ревью — свой модуль `lua/plugins/review/`** в стиле этого конфига
  (как `nvimtreeplug/`, `pytest_runner`): хранилище `.review/`, UI комментариев,
  интеграция LSP, цикл с Claude Code. Именно эти части не реализованы ни одним
  существующим плагином.
- **Отвергнутые альтернативы:**
  - `sindrets/diffview.nvim` — оригинал заброшен (июнь 2024); у форка
    `dlyongemallo` нет unified-режима вовсе, LSP только через `--imply-local`.
  - `georgeguimaraes/review.nvim` (★109, тоже на codediff) — закрывает ~90% UI,
    но хранит комментарии в `~/.local/share/nvim` с TTL 7 дней; форк = вечное
    обслуживание чужого кода ради замены хранилища. **Это официальный fallback**
    (см. этап 0) и донор идей (типы замечаний, ввод через floating window).
  - `reviewthem.nvim`, `choplin/code-review.nvim`, `postilla.nvim` — доноры идей:
    JSON-сессии, md-файлы в репо, «релокация» комментариев при сдвиге кода.
  - `octo.nvim` / `gitlab.nvim` — только с форджем, оффлайн невозможен.

## Формат хранения

Папка `.review/` в корне проекта. Файл создаётся только если по файлу есть
замечания; удаляется, когда замечаний не осталось. Источник истины о пути —
frontmatter `file:` (имя файла с `__` — для читаемости; коллизия путей с
настоящими `__` допустима, разрешается по frontmatter).

```markdown
---
file: src/app/main.py
base: a1b2c3d          # merge-base / левая ревизия
head: e4f5a6b          # ревизия, к которой привязаны номера строк
---

## L42
> if user.is_admin and not user.is_active:
Условие дублирует проверку из `check_access` выше — вынести в одну функцию.

## L57-L60
> for item in items:
>     process(item)
Здесь нужен батчинг: process дергает БД на каждой итерации.
```

Правила формата: `## L<N>` или `## L<N>-<M>` (диапазон), затем цитаты строк
кода с `>` (prr-стиль), затем текст замечания до следующего `##`. Формат
одновременно человекочитаем и парсится регуляркой.

## Жизненный цикл

1. `:ReviewOpen` — ревью текущей ветки от merge-base (или `:ReviewOpen A B`).
2. Пишем замечания в diff → они сразу сохраняются в `.review/*.md`.
3. `:ReviewPublish` — коммит `.review/` (история замечаний остаётся в git).
4. В Claude Code: `/fix-review` — читает `.review/*.md`, исправляет, **удаляет
   файлы замечаний** и коммитит. По истории git видно, какие были замечания.

## Этапы разработки

### Этап 0 — Spike codediff.nvim (полдня) ⚠ ворота для всего плана

Установить codediff.nvim (vim-plug, как остальные плагины конфига) и письменно
ответить да/нет:

1. Сравнение произвольных ревизий и merge-base (`A...B`) — какими командами?
2. Переключение side-by-side ⇄ inline на лету — работает?
3. Как из diff-буфера узнать: путь файла, ревизию, сторону (old/new), строку?
   (имена буферов, buffer-local переменные, публичный API, события/autocmd)
4. Можно ли ставить extmarks/signs/virtual lines в diff-буферы и переживают ли
   они перерисовку?
5. Расширяется ли панель файлов (значки «есть замечания»)? Если нет — можно ли
   узнать её буфер и патчить рендер (по опыту `nvimtreeplug/patch_build_nvim_tree.lua`)?
6. Можно ли открыть произвольный (неизменённый) файл внутри вкладки ревью?
7. На правой стороне при сравнении с worktree — настоящие буферы файлов
   (аттачится ли LSP)?

**Критерий:** если пункты 3–4 «нет» — уходим на fallback: форк
`georgeguimaraes/review.nvim` с заменой хранилища на `.review/*.md`.
Остальные «нет» лечатся своим кодом.

### Этап 1 — Хранилище и сессия (ядро без UI)

- `store.lua`: encode/decode пути (`/` ↔ `__`), парсер и сериализатор формата
  (round-trip тест на plenary/busted), CRUD замечаний, создание/удаление файлов
  по правилу «файл существует ⇔ есть замечания».
- `session.lua`: состояние ревью (base, head, список файлов `git diff
  --name-status base...head`), выбор ревизий через `vim.ui.select`/telescope
  (ветки → коммиты), default — merge-base с main/master.
- Команды `:ReviewOpen [base] [head]`, `:ReviewClose`.

**Критерий:** открытие diff по merge-base одной командой; `.review/*.md`
читаются и пишутся без потерь.

### Этап 2 — Комментарии в diff

- Маппинг в diff-буферах (`<leader>rc`, согласовать со стилем
  `vim/settings/keymaps.vim`): замечание к строке или визуальному выделению;
  ввод в floating window (markdown-подсветка).
- При сохранении — сразу запись в `.review/`, цитата строк подставляется
  автоматически из буфера.
- Отображение: sign в gutter + virtual lines под строкой (стиль GitLab);
  редактирование/удаление замечания под курсором; список всех замечаний
  (quickfix или telescope).

**Критерий:** полный цикл создать → увидеть → отредактировать → удалить;
файл замечаний исчезает вместе с последним замечанием.

### Этап 3 — Панель файлов и шапка

- Пометки в панели файлов: значок/счётчик замечаний у файла (способ — из
  ответа этапа 0: API, патч рендера или своя узкая панель).
- Winbar/tabline сверху: `base-ветка@hash ⇄ head-ветка@hash`, счётчики
  файлов и замечаний.
- Неизменённые файлы: команда открыть любой файл проекта внутри ревью —
  он добавляется в панель отдельной секцией («просмотренные»), показывается
  без diff.

**Критерий:** в панели видно, где есть замечания; неизменённый файл
открывается и остаётся в панели.

### Этап 4 — LSP-навигация

- `<C-CR>` (существующий умный goto из `lua/plugins/lsp/main.lua:110`)
  в правом (worktree) буфере: целевой файл открывается **внутри вкладки
  ревью** и добавляется в панель; если файл изменён в диапазоне ревью —
  открывается его diff, иначе обычный буфер. `<C-o>` возвращает назад.
- Ограничение (задокументировать): на левой (исторической) стороне LSP не
  работает — файлов этой ревизии нет на диске.

**Критерий:** прыжок из diff в определение в неизменённом файле; файл
появился в панели.

### Этап 5 — Цикл с Claude Code

- `:ReviewPublish` — `git add .review && git commit` с шаблонным сообщением.
- Команда для Claude: `.claude/commands/fix-review.md` в целевых проектах
  (шаблон хранить здесь, в папке плагина): прочитать все `.review/*.md`,
  найти места по трём якорям (номер → цитата → hash), исправить, удалить
  файлы замечаний, закоммитить. Если цитата не найдена — спросить, а не
  угадывать.
- `:ReviewDone` — ручное удаление `.review/*` + коммит (сценарий «исправил сам»).

**Критерий:** полный цикл на реальном проекте: ревью → publish →
`/fix-review` → замечания исправлены, `.review/` пуста, история в git.

### Этап 6 — Полировка

- Навигация `]r`/`[r]` по замечаниям, счётчик в airline
  (`vimairline/status_extras.lua`).
- Детект дрейфа: при открытии ревью сверять цитату с текущей строкой,
  помечать устаревшие замечания (⚠, как в postilla.nvim).
- Переименованные файлы (`git diff --find-renames`), пункт в quickui-меню
  (`vim/plugins/menu/main.vim`), опционально pre-commit-проверка «не мержить
  ветку с непустой `.review/`».

## Известные риски

- **codediff.nvim молод** (первая волна 2025–2026): API может меняться —
  прибить версию/commit в vim-plug; fallback описан в этапе 0.
- **«Разъезжающиеся» панели при скролле — виноват был терминал, не codediff:**
  WezTerm 20240203 некорректно обрабатывает synchronized output (DEC 2026)
  и склеивает куски кадров; в iTerm артефактов нет. Обход: `set notermsync`
  для WezTerm старше 2025 в `vim/settings/options.vim`; правильное лечение —
  обновить WezTerm, после этого блок можно удалить. Пин codediff снят,
  используется актуальная версия. Код ревью остался версионно-адаптивным
  (переживёт и откат на v2.52.x, если понадобится). Отдельно существует
  реальный, но транзиентный баг скролл-синка codediff
  [#518](https://github.com/esmuellert/codediff.nvim/issues/518) —
  следить не обязательно, к нашей проблеме отношения не имел.
- **Squash-merge стирает историю замечаний** из промежуточных коммитов ветки:
  если история ревью ценна — мержить ветку без squash.
- **`.review/` может утечь в main**, если агент забыл удалить — лечится
  опциональной проверкой из этапа 6.
- **Дрейф строк** после исправлений: замечания живут коротко
  (написал → исправили → удалили), а три якоря дают Claude найти место даже
  после сдвига.
